# 012 Secrets Managerのクロスリージョンレプリケーション

## 問題

あるアプリケーションは us-west-1 でホストされている。同社は us-east-1 に冗長性を追加したい。
アプリケーションのシークレットは us-west-1 の AWS Secrets Manager に保存されており、開発者はこのシークレットを us-east-1 にレプリケートする必要がある。

選択肢:
- 各シークレットのレプリケーションルールを作成する。宛先リージョンとして us-east-1 を設定し、シークレットの**ローテーション中に実行される**ルールを設定する。暗号化にはus-east-1のKMSキーを選択する
- Secrets Manager のライフサイクルルールを作成し、各シークレットを us-west-1 の新しい S3 バケットにレプリケートする。S3 レプリケーションルールで us-east-1 に転送する
- シークレットごとに us-east-1 に**新しいシークレットを作成**する。us-east-1 側でレプリケーションを設定し、ソースを us-west-1 の対応するシークレットに設定する。レプリケートされたシークレットの暗号化には**us-west-1のKMSキー**を選択する
- 各シークレットのレプリケーションを構成する。**レプリケーションリージョンとしてus-east-1を追加**する。暗号化にはus-east-1のKMSキーを選択する

正解: 4番目(各シークレットのレプリケーションを構成し、レプリケーションリージョンとしてus-east-1を追加。暗号化はus-east-1のKMSキーを使用)

## 選んだ答えと理由

選んだ: 3番目(us-east-1に新しいシークレットを手動作成し、ソースをus-west-1に設定。暗号化にはus-west-1のKMSキーを使用)(不正解)

理由:
- レプリケーション機能そのものの仕組みを理解しておらず、「レプリケーション=手動でコピーを作り、元(ソース)を指定する操作」というイメージで選択肢を評価していた
- 暗号化キーは「元データがあるリージョンのキーを使うもの」だと直感的に判断し、レプリカ先(us-east-1)ではなくソース側(us-west-1)のキーを選んでしまった

## 誤答の型

1. **サービスの守備範囲の誤解**: Secrets Managerには既存シークレットに対して「レプリカリージョンを追加する」だけで完結するネイティブなクロスリージョンレプリケーション機能があることを知らず、手動で別シークレットを作成してソースを指定するという、実際には存在しない操作感で選択肢を組み立ててしまった
2. **用語未知(暗号化キーのリージョン原則)**: レプリカの暗号化キーは常に「レプリカが存在するリージョン」のKMSキーを使うべきという原則を知らず、「ソース側のキーを使う」という誤ったメンタルモデルを持っていた

## 仮説

- Secrets Managerのレプリケーションは、既存のプライマリシークレットに対して設定する機能であり、レプリカ用に別のシークレットを新規作成する必要はないはず
- レプリケーションはローテーションの実行タイミングとは無関係に、シークレットの値が変更されるたびに自動的にレプリカへ同期されるはず
- レプリカは読み取り専用であり、値の更新は常にプライマリ側でのみ行えるはず
- 暗号化キーはレプリカが存在するリージョン(us-east-1)のKMSキーを指定すべきで、ソースリージョン(us-west-1)のキーを使うと、us-west-1に障害が起きた際にus-east-1側のレプリカも復号できなくなり、DR(災害復旧)の目的を果たせなくなるはず

## 検証

> 実機デプロイは行っていない(標準ではコード整備までを完了条件とする方針。[CLAUDE.md](../../CLAUDE.md)「AWS実行について」参照)。以下はユーザーが実行を希望した場合の検証手順として設計したもの。

1. [`01_create_secret.sh`](01_create_secret.sh): `us-west-1` にプライマリシークレット(`dva-012-secretsmanager-replication`)を作成する
2. [`02_create_kms_key.sh`](02_create_kms_key.sh): `us-east-1` にレプリカ暗号化専用のカスタマー管理KMSキーを作成する(ソース側のキーを流用しないことがポイント)
3. [`03_add_replica.sh`](03_add_replica.sh): `replicate-secret-to-regions` で既存のプライマリシークレットに対し `us-east-1` をレプリカリージョンとして追加する。新規シークレットの作成やローテーションルールとの関連付けは不要であることを確認する
4. [`04_check_replication.sh`](04_check_replication.sh):
   - `describe-secret` の `ReplicationStatus` でレプリカの同期状態(`InSync`)を確認
   - レプリカ側(`us-east-1`)から `get-secret-value` で値が読み取れることを確認
   - レプリカ側へ `put-secret-value` を試み、**読み取り専用のため失敗する**ことを確認
   - プライマリ側(`us-west-1`)を更新し、しばらくしてからレプリカ側の値が自動的に追従することを確認(ローテーションとは無関係に、値の変更だけをトリガーに同期される)

期待する結果:
- レプリカの作成に新規シークレットの手動作成は不要で、既存シークレットへの設定追加だけで完結する
- レプリカへの直接書き込みはエラーになる(更新は常にプライマリ側で行う)
- プライマリの更新は、ローテーションの有無に関わらずレプリカへ自動同期される

## 結論(1行)

> Secrets Managerのクロスリージョンレプリケーションは、既存シークレットに「レプリカリージョンを追加する」だけで完結するネイティブ機能で、ローテーションとは無関係に値の変更のたびに自動同期される。レプリカは読み取り専用で、暗号化キーは(ソース側ではなく)レプリカが存在するリージョンのKMSキーを指定する。

## 片付け

[`05_delete.sh`](05_delete.sh)で レプリカリージョンの解除(`remove-region-from-replication`) → プライマリシークレットの削除(即時・復旧不可) → KMSキーの削除スケジュール(us-east-1、最短7日後)、の順に削除する。KMSキーは即時削除できない点に注意。
