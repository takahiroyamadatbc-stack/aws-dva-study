# CloudFrontカスタムドメイン: ACM証明書リージョンとRoute 53レコード種別

## 1. ACM証明書のリージョン要件(サービス別まとめ)

証明書をどのリージョンのACMに置くべきかは、**証明書を直接参照するサービスが何か**で決まる。「背後のオリジン/APIがどこにあるか」は無関係。

| 参照するサービス | 証明書リージョン | 理由 |
|---|---|---|
| CloudFront(ディストリビューションのカスタムドメイン) | 常に **us-east-1** 固定 | CloudFrontはグローバルサービスで、証明書配布の仕組み上us-east-1のACMしか参照できない |
| API Gateway エッジ最適化(EDGE)カスタムドメイン | **us-east-1** 固定 | 内部的にCloudFrontを使うため、CloudFrontと同じ制約を継承する |
| API Gateway リージョナル(REGIONAL)カスタムドメイン | APIと**同一リージョン** | CloudFrontを経由しないため、APIのリージョンでTLS終端する |
| ALB/NLBのリスナー証明書 | ALB/NLBと**同一リージョン** | ロードバランサー自体がリージョナルリソースのため |

引っかけパターン: 「API GatewayがusEast-2にある」という情報を見て、CloudFrontを挟んでいるにもかかわらず「証明書もus-east-2」と判断してしまう([Lab011](README.md)の誤答パターン)。**CloudFrontが関与するかどうか**を最初に確認する。

## 2. Route 53のレコード種別: A / Aエイリアス / CNAME

| 種別 | DNS上の意味 | ターゲット | zone apexで使える | 追加料金 | AWSリソースのIP変更への追従 |
|---|---|---|---|---|---|
| 通常のAレコード | ホスト名→IPアドレス | 固定IPを直接記述 | ○ | なし | 追従しない(手動更新が必要) |
| CNAME | ホスト名→ホスト名 | 他のDNS名(AWS外でも可) | × (DNS標準の制約) | なし | ホスト名解決なので追従はするが、DNSルックアップが1段増える |
| **Aレコード(エイリアス)** | Route 53独自拡張。見た目はAだが実体はRoute 53内部でのAWSリソース参照 | ALB / CloudFront / S3ウェブサイト / 別のRoute 53レコード等 | ○ | **なし** | **自動追従**(Route 53がAWS側の変更を追跡) |

CloudFront・ALB・S3静的サイトなど、**エッジIPやノードIPが変動するAWSマネージドサービス**をRoute 53から指す場合は、原則としてAレコード(エイリアス)を使う。CNAMEは「AWS外の任意のホスト名」やzone apexではないサブドメインで、かつAWSリソースへの最適化が不要な場面向け。

## 3. この問題の選択肢別の判断根拠

| 選択肢 | 証明書リージョン | レコード種別 | 判定 | 不正解の理由 |
|---|---|---|---|---|
| us-east-1 ACM + A(エイリアス) | ○ 正しい | ○ 正しい | **正解** | - |
| API Gatewayと同リージョン(us-east-2) ACM + 通常のAレコード | × | × | 不正解 | 証明書リージョンもレコード種別も誤り。IPを固定管理する構成はCloudFrontのIP変動に追従できない |
| CloudFrontへの証明書直接アップロード + CNAME | (該当なし) | △ | 不正解 | CloudFrontは証明書を直接アップロードする機能を持たない(ACM/IAM経由が必須) |
| us-east-2 ACM + CNAME(選んで間違えた) | × | △ | 不正解 | 証明書リージョンが誤り。CNAME自体は技術的に成立し得るが、ベストプラクティスはAレコード(エイリアス) |

## 一行結論

> CloudFrontが絡む時点で証明書は無条件でus-east-1、Route 53でCloudFrontを指す時はAレコード(エイリアス)一択。「同一リージョン」ルールが効くのはAPI Gatewayのリージョナルカスタムドメインなど、CloudFrontを経由しないケースに限られる。
