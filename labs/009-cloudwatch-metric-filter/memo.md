# CloudWatch Logsでのキーワード検知通知(メトリクスフィルター)

## 問題

ログに「ERROR」が出たらSNS経由でメールを飛ばしたい。次に行うべき作業はどれか。

正解: ロググループに「ERROR」を検索語とするCloudWatchメトリクスフィルターを作成し、そのメトリクスが1以上になったらSNSに通知するアラームを作成する。

## 誤答の型

選んだ: 「フィルターパターン『ERROR』を設定し、ロググループディメンションとSNSトピック送信先を含むCloudWatchアラームを作成する」

CloudWatchアラームは**メトリクス**しか監視できず、ログそのものを直接監視することはできない。「ログ→メトリクス」への変換ステップ(メトリクスフィルター)が別リソースとして必要という前提を知らなかった。

## 仕組み: 2段構成

```
ロググループ → [メトリクスフィルター] → カスタムメトリクス → [アラーム] → SNS → メール
```

- **メトリクスフィルター**: ロググループに到着するログイベントをリアルタイムで走査し、フィルターパターンにマッチした回数(または抽出値)をカスタムメトリクスとして記録する。ログ→メトリクスの変換装置
- **アラーム**: メトリクスのしきい値を監視し、超過時にSNS等へ通知する。メトリクス→通知の変換装置

アラームはメトリクスフィルターが生成したメトリクスにしか反応できない。フィルターパターンを直接アラームに渡すことはできない。

## 誤答の判断基準

| 選択肢 | 判断 | 理由 |
| --- | --- | --- |
| メトリクスフィルター作成 → アラーム作成 | 正解 | ログ→メトリクス→通知の正しい2段構成 |
| CloudWatch Logs Insightsでメトリクスクエリ | 誤り | Insightsは対話的なアドホッククエリツール。継続監視の仕組みではなく、クエリ結果から直接アラームは作れない |
| 「SNSサブスクリプションフィルター」を作成 | 誤り | そのような機能は存在しない。ログのサブスクリプションフィルターはKinesis Data Streams/Firehose/Lambdaへの転送用で、SNSへの直接配信はできない |
| フィルターパターンを直接アラームに設定(選んで間違えた) | 誤り | アラームはメトリクスしか監視できず、ログのフィルターパターンを直接渡すインターフェースはない |

## 押さえておくべき落とし穴

- **さかのぼり適用されない**: メトリクスフィルターは作成後に到着するログイベントにのみ適用される。過去ログには効かない
- **`defaultValue`と`treat-missing-data`**: マッチしない期間はメトリクスにデータポイントが送られない。デフォルト値や欠測データの扱いを誤ると、アラームが`INSUFFICIENT_DATA`のまま張り付く
- **フィルターパターン構文**: 単純なテキスト検索の他、JSON構造化ログ用パターン(`{ $.level = "ERROR" }`)もある

## 検証の流れ(このLabのスクリプト)

1. `01_create_resources.sh`: ロググループ、SNSトピック＋メールサブスクリプション、「ERROR」にマッチするメトリクスフィルター(`ErrorCount`)、`ErrorCount`のSumが1以上で通知するアラームを作成(`NOTIFY_EMAIL=you@example.com`で実行。購読確認メールのリンクをクリックしないと通知は届かない)
2. `02_generate_logs.sh`: `ERROR`を含む行2件、含まない行3件を送信
3. `03_check_metric_and_alarm.sh`: `ErrorCount`メトリクスの値とアラーム状態を確認

期待する結果: `ErrorCount`にERROR行の件数(2)のみが記録され、アラームが`ALARM`に遷移する。

## 結論

CloudWatchアラームはメトリクスしか監視できないため、ログ内の文字列検知にはまずメトリクスフィルターでログをカスタムメトリクスに変換する必要がある。フィルターパターンを直接アラームに渡すことはできない。
