# 008 ALB配下のEC2でクライアントの実IPをログに残す(X-Forwarded-For)

## 問題

開発者が、Amazon EC2 インスタンスへのトラフィックを分析するアプリケーションを作成している。EC2インスタンスは、パブリックなApplication Load Balancer (ALB) の背後で実行される。HTTPサーバーがEC2インスタンス上で動作し、すべてのリクエストをログファイルに記録する。

開発者はクライアントのパブリックIPアドレスを取得したいが、ログファイルにはALBのIPアドレスしか記録されていないことに気づいた。クライアントのパブリックIPアドレスをログファイルに記録する最適な方法を選ぶ問題。

選択肢:
- 各EC2インスタンスにAWS X-Rayデーモンをインストールし、ログファイルに書き込むよう設定する
- HTTPサーバーのログ設定ファイルに`X-Forwarded-For`ヘッダーを追加する
- 各EC2インスタンスにAmazon CloudWatch Logsエージェントをインストールし、ログファイルに書き込むよう設定する
- HTTPサーバーのログ設定ファイルに`Host`ヘッダーを追加する

正解: 「HTTPサーバーのログ設定ファイルに`X-Forwarded-For`ヘッダーを追加する」

## 選んだ答えと理由

選んだ: 「各EC2インスタンスにAWS X-Rayデーモンをインストールし、ログファイルに書き込むよう設定する」(不正解)

理由: 「アプリケーションのトラフィックを分析する」という問題文に引きずられ、X-Rayを「リクエストの詳細を収集して記録してくれる汎用的な分析エージェント」だと捉えていた。X-Rayが分散トレーシング(実行経路・所要時間の可視化)に特化したサービスであり、任意のログファイルへの書き込み機能自体を持たないことを認識できていなかった。

## 誤答の型

サービスの守備範囲の誤解: X-Rayを「トラフィックを分析するなら何でも使えるツール」と拡大解釈し、実際の機能範囲(分散トレーシング専用、ログファイルへの書き込み機能なし)を確認しなかった。

同時に、「ALBはプロキシとして動作するため、クライアントの送信元IPをバックエンドに転送するにはヘッダーで運ぶしかない」という、プロキシ経由時のHTTP通信の基本構造への理解も不足していた。

## 仮説

ALBはL7で動作するリバースプロキシであり、バックエンドEC2から見ると送信元IPは常にALBのノードのIPになる(TCP接続自体がALB→EC2間で新規に張られるため)。そこでALBは元のクライアントIPを`X-Forwarded-For`ヘッダーに設定してリクエストを転送する。

- HTTPサーバー(nginx/Apache/IIS)は受け取ったヘッダーをそのままログに出力できるので、`log_format`(nginx)や`LogFormat`(Apache)にこのヘッダーを追加するだけで実際のクライアントIPが記録できるはず
- X-RayやCloudWatch Logsエージェントは、いずれも「既存のログの収集・可視化・転送」を担うもので、ログの中身(どのフィールドを書くか)を決めるのはHTTPサーバー自身の設定であり、これらのサービスの守備範囲ではないはず

## 検証

> 実機デプロイは行っていない(標準ではコード整備までを完了条件とする方針。CLAUDE.md「AWS実行について」参照)。以下はユーザーが実行を希望した場合の検証手順として設計したもの。

1. [`01_create_ec2_alb.sh`](01_create_ec2_alb.sh): デフォルトVPCの2AZに、SSM接続用IAMロールを持つEC2インスタンス([`src/user_data.sh`](src/user_data.sh)でnginxをインストールし、`$remote_addr`と`$http_x_forwarded_for`を両方記録する`xff_log`フォーマットを追加)を1台起動し、ターゲットグループ経由でinternet-facingなALBにぶら下げる
2. [`02_generate_requests.sh`](02_generate_requests.sh): ALBのDNS名に対してローカル(手元の端末)から`curl`を3回実行する
3. [`03_check_access_log.sh`](03_check_access_log.sh): SSM Run Commandで`/var/log/nginx/xff-access.log`の末尾を取得し、`remote_addr`(ALBノードのIP)と`x_forwarded_for`(手元の端末のパブリックIP)を突き合わせる

期待する結果: `remote_addr`は常にALB側のIP(VPC内のプライベートIP)になる一方、`x_forwarded_for`には`curl`を実行した端末の実際のパブリックIPが記録され、両者が一致しないことでALBがプロキシとして動作していることが確認できる。

## 結論(1行)

> ALB配下ではバックエンドから見た送信元IPは常にALBのものになるため、クライアントの実IPは`X-Forwarded-For`ヘッダーに載って渡ってくる。HTTPサーバーのログ設定(`log_format`/`LogFormat`)にこのヘッダーを追加するだけで記録できる話であり、X-Ray(トレーシング専用)やCloudWatch Logsエージェント(ログ収集専用)はログの中身を追加・加工する機能を持たないため的外れ。
