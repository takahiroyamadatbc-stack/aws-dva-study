# AMIライフサイクルとセキュリティ最新化のタイミング整理

## 1. 「イメージ数最小化」はAMIに何を焼き込むかで決まる

| 構成 | AMIの更新頻度 | 理由 |
|---|---|---|
| AMIにOS + パッチ + エージェントのみ | 低頻度（週1〜月1程度） | アプリは含まれないため、アプリのリリース頻度とAMI更新が分離される |
| AMIにアプリまで焼き込む | アプリのリリース頻度そのまま（週複数回） | アプリが変わるたびにAMIを作り直す必要がある |

EC2 Image Builderは「AMIを作る仕組み」であって「AMIを増やす原因」ではない。むしろ**責務分離（OS/パッチ層 = Image Builder、アプリ層 = CodeDeploy）**を実現する道具であり、除外する理由にはならない。

## 2. AMIのライフサイクル全体像

```
[ソースAMI選択]
      ↓
[Image Builderパイプライン実行]
   ├─ Build: ベースAMIにコンポーネント(パッチ/エージェント)を適用
   ├─ Test: 検証(Image Builder標準テスト or カスタムテスト)
   └─ Distribution: リージョン間コピー、アカウント間共有、タグ付け、SSMパラメータへのAMI ID公開
      ↓
[新AMI発行(バージョン管理: x.y.z)]
      ↓
[Auto Scaling起動テンプレートが最新AMIを解決(resolve:ssm:<パラメータ名>)]
      ↓
[インスタンスリフレッシュ or 次回スケールアウトから新AMI適用]
      ↓
[旧AMIの非推奨化 (Deprecation)]
      ↓
[旧AMIの登録解除 (Deregister)]
      ↓
[裏側のEBSスナップショット削除]
```

### 各フェーズの詳細

- **① 作成(Build)**: Image Builderの「イメージレシピ」がベースAMI + コンポーネント（パッチ適用、CodeDeployエージェント導入など）を定義。パイプラインはスケジュール実行可能（例: 毎週日曜3時に最新セキュリティパッチを取り込んで再ビルド）で、「常に最新のセキュリティアップデートを適用」要件はここで満たせる
- **② 検証(Test)**: Image Builderのvalidate/testフェーズで、起動確認やパッチ適用確認などのテストを自動実行できる。これが「イメージは検証される必要がある」の直接的な根拠
- **③ 世代管理(Versioning)**: AMIは自動的にセマンティックバージョン（例: 1.0.3）が付与され、パイプライン実行ごとに新しいAMIバージョンとして記録される。古いAMIをすぐ消さず複数世代を並行保持できる（ロールバック用）
- **④ 非推奨化(Deprecation)**: `deregister-image`の前段階として`enable-image-deprecation`がある。非推奨化されたAMIは「新規の起動テンプレートやAuto Scalingグループから選びにくくする」目的のマークで、既存の参照は引き続き動作する
- **⑤ 登録解除(Deregister)**: AMI自体（メタデータ）を削除。これを行うとそのAMIから新規インスタンス起動は不可能になる。ただし**裏側のEBSスナップショットは自動削除されない**（典型的な消し忘れポイント）
- **⑥ スナップショット削除**: `deregister-image`後、関連スナップショットは手動またはData Lifecycle Manager(DLM)のポリシーで削除する必要がある

## 3. セキュリティ最新化：いつ・どのサービスが担当するか

「セキュリティの最新化」は対象インスタンスが「これから起動するもの」か「すでに稼働中のもの」かでタイミングと担当サービスが変わる。

| タイミング | 対象 | サービス | 何をするか |
|---|---|---|---|
| ① AMIビルド時 | まだ存在しない、これから起動するインスタンス | **EC2 Image Builder** | パイプラインのコンポーネントとして`yum update`/`apt-get upgrade`相当やAWS提供の「Update OS」コンポーネントを実行し、その時点の最新パッチを含んだ新AMIを生成 |
| ② 新規起動時（スケールアウト） | Auto Scalingが新しく起動するインスタンス | 起動テンプレート＋Image Builderで作った最新AMI | 起動時点でOSがすでにパッチ済みの状態からブートするだけ（UserDataでの追加パッチ作業が不要になり起動が速い） |
| ③ 稼働中インスタンス | 今まさに動いている既存インスタンス群 | **AWS Systems Manager Patch Manager** | パッチベースライン＋メンテナンスウィンドウで、稼働中インスタンスに定期的にin-placeでパッチ適用 |
| ④ 既存インスタンスの入れ替え | 稼働中インスタンス群をまるごと新AMI世代へ | **Auto Scaling Instance Refresh** | Patch Managerを使わず、新しいパッチ済みAMIで既存インスタンスを段階的に再作成して置き換える |

### ポイント: ①と③は別物

- Image Builderがパッチを当てるのは「AMI」に対してだけで、すでに起動して稼働しているインスタンスには何の影響も与えない。新AMIは「次に起動するインスタンス」にしか効かない
- 稼働中インスタンスにパッチを反映させるには、(a) Patch Managerで直接当てる、(b) Instance Refreshでインスタンスごと新AMI世代に入れ替える、のどちらかが必要

### 「常に最新」を維持するトリガー

Image Builderのパイプライン実行は放置すると陳腐化するため、以下のようなトリガーで定期実行させる。

- **スケジュール実行**: パイプラインに定期スケジュール（例: 毎週）を設定（このLabでは`cron(0 3 ? * SUN *)`）
- **イベント駆動**: ベースOSのAMI更新（Amazon Linux 2023の新AMIリリースなど）をEventBridgeで検知し、自動的にImage Builderパイプラインを再実行

## 4. 誤答の選択肢が的外れな理由(整理)

| 選択肢 | 判断 | 理由 |
|---|---|---|
| Image Builderでアプリまで焼き込む | 不正解 | 起動時間は短縮されるが、アプリが週複数回更新されるためAMIも週複数回作り直しになり「イメージ数最小化」に違反する |
| CodePipelineでデプロイ | 不正解 | CodePipelineはCI/CDのオーケストレーションサービスで、実際のデプロイ処理自体は行わない。デプロイはCodeDeployなど別サービスが担当する |
| セキュリティアップデートをcronで延期 | 不正解 | 「利用可能なすべてのセキュリティアップデートを適用する」に明確に違反。トラフィックを処理し始める時点で脆弱性のある状態になる |

## 5. 試験でのキーワード対応

| 設問の語 | 対応する答え |
|---|---|
| イメージ数を最小限に抑えたい | アプリをAMIに含めない（OS+パッチ+エージェントのみAMI化） |
| 常にアプリの最新バージョンを利用可能にしたい | AWS CodeDeploy（起動後にデプロイ） |
| セキュリティアップデートを常に適用したい（新規起動インスタンス） | EC2 Image Builderのパイプラインでビルド時にパッチ適用 |
| セキュリティアップデートを稼働中インスタンスにも適用したい | AWS Systems Manager Patch Manager |
| イメージの検証が必要 | EC2 Image Builderのvalidate/testフェーズ |
| 「オーケストレーション」に釣られてCodePipelineを選びたくなる | CodePipelineはデプロイ実行者ではなくパイプライン管理者。的外れ |

## 参考: このLabで使ったツール

| ツール | 役割 |
|---|---|
| EC2 Image Builder | AMI作成・検証・配布・世代管理の自動化 |
| AMI Deprecation | 古いAMIを新規起動対象から外す（削除ではない） |
| Data Lifecycle Manager (DLM) | スナップショット/AMIの保持世代数ポリシーに基づく自動削除 |
| 起動テンプレートの`resolve:ssm:`動的パラメータ | Auto ScalingグループがImage Builderの最新AMIを自動追従できる |
| AWS CodeDeploy | Auto Scalingグループへのアプリ自動デプロイ（スケールアウト時も自動適用） |
