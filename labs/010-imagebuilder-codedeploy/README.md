# 010 EC2 Image Builder + CodeDeployでスケールアウト時間を短縮する

## 問題

アプリケーションがAmazon EC2 Auto Scalingグループを使用している。開発者は、スケールアウトイベント中にEC2インスタンスが利用可能になるまでに長い時間がかかることに気付いた。UserDataスクリプトの実行に時間がかかっている。アプリケーションは頻繁に更新され、週に複数回の新バージョンがリリースされる。

開発者は、EC2インスタンスが利用可能になるまでの時間を短縮するソリューションを実装する必要がある。ソリューションは、アプリケーションの最新バージョンを常に利用可能にし、利用可能なすべてのセキュリティアップデートを適用する必要がある。また、作成されるイメージの数を最小限に抑える必要がある。イメージは検証される必要がある。（2つ選択）

選択肢:
- EC2 Image Builderを使用してAMIを作成する。アプリケーションを管理・実行するために必要なすべてのパッチとエージェントをインストールする。Auto Scalingグループの起動設定をこのAMIを使うよう更新する（**正解**）
- AWS CodeDeployをセットアップして、実行時にアプリケーションの最新バージョンをデプロイする（**正解**）
- EC2 Image Builderを使用してAMIを作成する。アプリケーションの最新バージョンと、パッチ・エージェントをすべてインストールする。Auto Scalingグループの起動設定をこのAMIを使うよう更新する
- AWS CodePipelineをセットアップして、実行時にアプリケーションの最新バージョンをデプロイする
- セキュリティアップデートの適用をインスタンス起動後のcronジョブによるスケジュールタスクに延期して、起動時間を短縮する

## 選んだ答えと理由

選んだ: 「AWS CodeDeployをセットアップして、実行時にアプリケーションの最新バージョンをデプロイする」のみ選択し、「EC2 Image Builderを使用してAMIを作成する（アプリは含めない）」を選ばなかった（1つ不足で不正解）。

理由: 「作成されるイメージの数を最小限に抑える」という要件を見て、「イメージを作る操作自体を増やしたくない」と読み違え、EC2 Image Builderを候補から外してしまった。Image Builderを使うこと自体がイメージ数を増やす原因だと誤解していた。

## 誤答の型

サービスの守備範囲の誤解: EC2 Image Builderを「AMIを作るたびにイメージが増える仕組み」とひとくくりに捉え、**何をAMIに焼き込むか（OS+パッチ+エージェントのみ／アプリまで含めるか）でイメージ更新頻度が決まる**という構造を見落としていた。「イメージ数最小化」はツールの選択ではなく、AMIとアプリの責務分離で解決する要件だった。

## 仮説

- AMIにアプリケーション本体を含めなければ、アプリがどれだけ頻繁にリリースされてもAMI自体は更新不要（＝イメージ数は増えない）。AMI更新はOSパッチ適用など低頻度なタイミングだけでよいはず
- Image BuilderパイプラインはAMIの作成・検証（validate/testフェーズ）・配布を自動化でき、「イメージは検証される」要件を満たす
- 起動テンプレートのImageIdに`resolve:ssm:<パラメータ名>`を指定し、Image Builderの配布設定でAMI IDをSSMパラメータへ自動公開すれば、Auto Scalingグループは常に最新パッチ済みAMIから起動でき、手動での起動テンプレート更新も不要になるはず
- アプリの配布はCodeDeployが担当し、デプロイグループにAuto Scalingグループを紐づけることで、スケールアウトで新規起動したインスタンスにも自動的に最新バージョンがデプロイされるはず

## 検証

> 実機デプロイは行っていない(標準ではコード整備までを完了条件とする方針。CLAUDE.md「AWS実行について」参照)。以下はユーザーが実行を希望した場合の検証手順として設計したもの。

1. [`01_create_iam_roles.sh`](01_create_iam_roles.sh): Image Builderのビルド/テスト用インスタンスロール、Auto Scalingで起動するアプリ用インスタンスロール、CodeDeployサービスロールを作成
2. [`02_create_image_pipeline.sh`](02_create_image_pipeline.sh): [`src/component-document.yml`](src/component-document.yml)（OSセキュリティパッチ適用 + CodeDeployエージェント導入のみ、アプリは含めない）をコンポーネント化し、インフラ設定・イメージレシピ・配布設定（AMI IDをSSMパラメータへ自動公開）・イメージパイプライン（毎週日曜3時UTCに再ビルド）を作成し、初回ビルドを起動
3. [`03_create_launch_template_and_asg.sh`](03_create_launch_template_and_asg.sh): ImageIdに`resolve:ssm:/dva-010/imagebuilder-codedeploy/latest-ami`を指定した起動テンプレートとAuto Scalingグループを作成
4. [`04_create_codedeploy_app.sh`](04_create_codedeploy_app.sh): CodeDeployアプリケーション・デプロイグループ（Auto Scalingグループに紐付け）を作成し、[`src/appspec.yml`](src/appspec.yml)とダミーのデプロイスクリプトをリビジョンとしてpush・デプロイ
5. [`05_check_pipeline_and_ami_lifecycle.sh`](05_check_pipeline_and_ami_lifecycle.sh): パイプラインのビルド履歴、SSMパラメータが指す最新AMI、ASG状態、CodeDeployデプロイ状況を確認し、AMIライフサイクル操作（非推奨化→登録解除→スナップショット削除）の実行例を提示

期待する結果: AMIはOS層のみを保持するため週次程度の更新頻度に抑えられ（イメージ数最小化）、アプリの週複数回のリリースはCodeDeployのデプロイ回数としてのみ増える。スケールアウト時は起動テンプレートが常に最新パッチ済みAMIを解決し、UserDataでのパッチ適用待ちが発生しないため起動時間が短縮される。

セキュリティアップデート適用のタイミングとサービスの対応関係、AMIライフサイクル管理の詳細は[`memo.md`](memo.md)を参照。

## 結論（1行）

> 「イメージ数最小化」はImage Builderを使うか否かではなく、AMIに何を焼き込むか（アプリを含めずOS+パッチ+エージェントのみにする）で決まる。アプリはAMIの外でCodeDeployにより配布すれば、「最新バージョン常時利用可能」「セキュリティアップデート適用」「イメージ検証」「イメージ数最小化」の4要件をImage Builder+CodeDeployの組み合わせで両立できる。
