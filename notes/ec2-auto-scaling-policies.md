# EC2 Auto Scaling ポリシー横断整理

Auto Scaling グループ（ASG）のスケーリングポリシーの種類と使い分け。
「どのシナリオでどのポリシーを選ぶか」を問う設問が多いので、キーワード対応を軸にまとめる。

## ポリシーの種類

| ポリシー | 仕組み | クールダウン/ウォームアップ | ユースケース | 検証Lab |
| --- | --- | --- | --- | --- |
| Target Tracking Scaling | 指定した指標（例: CPU使用率50%）を目標値に保つよう、必要なアラームをAWSが自動生成して増減 | 内部的にウォームアップ期間を使用（デフォルト300秒、ユーザーが直接クールダウンを意識する場面は少ない） | 「特定の指標を一定値に維持したい」。AWS推奨のデフォルト選択 | |
| Step Scaling | CloudWatchアラームの**超過量に応じて段階的に**スケーリング量を変える（例: 閾値+10%なら+1台、+20%なら+3台） | クールダウンではなく**ウォームアップ期間**。ウォームアップ中のインスタンスは集計上「起動中」として扱われ、複数ステップが重なった場合も再評価に反映される | 「負荷の大きさに応じて増減量を変えたい」「急激な負荷変動に段階的に対応したい」 | |
| Simple Scaling | 1つのCloudWatchアラームに対して1つの固定アクション（例: +1台） | **クールダウン期間**（デフォルト300秒）。期間中は新たなスケーリングアクティビティを一切開始しない＝古い方式で細かい調整に弱い | 現在はAWSが非推奨、レガシー構成の理解用 | |
| Scheduled Scaling | 日時を指定してキャパシティ（Min/Max/Desired）を変更 | 該当なし（指定時刻に実行するだけ） | 「毎日決まった時間帯にアクセスが増える」など予測可能な周期的負荷 | |
| Predictive Scaling | 機械学習で過去の負荷パターンから将来（最大48時間先）を予測し、事前にキャパシティを用意 | 該当なし | 「周期的だが手動スケジュールほど単純でない」「事前にスケールアウトを完了させ、負荷発生時点で間に合わせたい」。最低24時間分の履歴データが必要 | |

## 判断基準（キーワード対応）

| 設問のキーワード | 答え |
| --- | --- |
| 「一定の使用率を維持」「シンプルに設定したい」 | Target Tracking Scaling |
| 「超過量に応じて増減幅を変えたい」「段階的に」 | Step Scaling |
| 「1つの固定量だけ増減」「レガシー」 | Simple Scaling |
| 「毎日/毎週決まった時間に増減」「予測可能なスケジュール」 | Scheduled Scaling |
| 「過去のトラフィックパターンから予測」「機械学習」「事前にプロビジョニング」 | Predictive Scaling |
| 複数ポリシーが同時にトリガーされたらどうなるか | スケールアウトが優先される（インスタンス数が多くなる方のアクションが採用される） |

## 補足で混同しやすい点

- **クールダウン（Simple Scaling）とウォームアップ（Step/Target Tracking）は別概念**。クールダウンは「次のアクションを一定時間待つ」、ウォームアップは「起動中インスタンスを集計にどう含めるか」の違い。
- Target Tracking / Step Scaling はいずれも内部でCloudWatchアラームを使うが、**Target Trackingはアラームをユーザーが意識しなくてよい**（AWSが目標値から自動生成）のに対し、Step Scalingは**閾値と増減幅の対応表を自分で定義**する必要がある。
- Predictive Scalingは「予測のみ」モードと「予測に基づき自動でスケーリングポリシーに反映」モードがあり、まず予測結果を確認してから有効化する運用が可能。
- スケールインの保護（Instance Scale-In Protection）はライフサイクルフックとは別機能。処理中のインスタンスが不用意に終了されないようにする用途で使う。

## ウォームアップ / クールダウン / ヘルスチェック / ライフサイクルフックの違い

名前も発生タイミングも似ていて混同しやすい4つの待機・判定系機能を整理する。**「何を待つためのものか」で区別する**のがコツ。

| 項目 | 何のための待機/判定か | 発生タイミング | デフォルト値 | 設定単位 |
| --- | --- | --- | --- | --- |
| ウォームアップ期間（Warm-up） | 新規起動インスタンスのメトリクスが安定するまで、**スケーリング判断の集計対象から除外**する | スケールアウトでインスタンス起動直後（Step Scaling / Target Tracking） | 300秒 | ポリシー単位（Step Scalingは`EstimatedInstanceWarmup`） |
| クールダウン期間（Cooldown） | 直前のスケーリングアクションの効果が反映されるまで、**次のスケーリングアクティビティ自体を開始しない** | Simple Scalingでアクション実行直後 | 300秒 | ASG単位 / ポリシー単位で上書き可 |
| ヘルスチェック猶予期間（Health Check Grace Period） | 起動直後のインスタンスが**まだアプリの初期化中でヘルスチェックに応答できない状態**を、異常とみなさない | インスタンス起動直後 | 300秒（ELBヘルスチェック併用時は起動時間に応じて延長推奨） | ASG単位 |
| ライフサイクルフック（Lifecycle Hook） | `Pending:Wait` / `Terminating:Wait` 状態で**インスタンスを保留し、任意のカスタム処理**（設定投入、ログ退避、SNS/Lambda通知など）を挟む | インスタンスの起動完了直前・終了開始直前 | タイムアウト3600秒（ハートビートで延長可、最大172800秒=48時間） | ライフサイクルフック単位 |

### 判断基準（キーワード対応・待機/判定系）

| 設問のキーワード | 答え |
| --- | --- |
| 「起動直後のインスタンスをスケーリング判断の母数に含めたくない」 | ウォームアップ期間 |
| 「スケーリングアクション後、一定時間は新たなアクションを起こしたくない」（Simple Scaling文脈） | クールダウン期間 |
| 「起動直後のインスタンスが不健全と誤判定されて終了されてしまう」 | ヘルスチェック猶予期間を延ばす |
| 「インスタンス終了前に後処理（ログ収集など）を挟みたい」「起動完了前に初期設定を完了させたい」 | ライフサイクルフック（`Terminating:Wait` / `Pending:Wait`） |
| ヘルスチェックの判定元をEC2ステータスだけでなくロードバランサーの判定にも合わせたい | ヘルスチェックタイプを`ELB`（または`EC2,ELB`）に設定 |

### ヘルスチェックタイプの違い

- **EC2ステータスチェック**: インスタンス自体の起動状態のみを見る。デフォルト。
- **ELBヘルスチェック**: ターゲットグループのヘルスチェック（アプリケーションレベル）結果も判定に使う。ASGにELBをアタッチしていても、ヘルスチェックタイプを明示的に`ELB`にしないとEC2ステータスのみで判定され続ける点に注意。
- いずれかで不健全判定 → ASGが自動的にそのインスタンスを終了し、新しいインスタンスに置き換える。

### ライフサイクルフックの流れ（イメージ）

1. スケールアウト時: `Pending` → **`Pending:Wait`（ここでフック発火、カスタム処理を待つ）** → `Pending:Proceed` → `InService`
2. スケールイン時: `Terminating` → **`Terminating:Wait`（ここでフック発火）** → `Terminating:Proceed` → `Terminated`
3. タイムアウトが来る前に`CompleteLifecycleAction`を呼ぶか、`RecordLifecycleActionHeartbeat`でタイムアウトを延長する必要がある
