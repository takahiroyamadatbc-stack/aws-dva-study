# セキュリティ・権限メモ

IAM、KMS、Secrets Manager／Parameter Store周りの暗記事項。

## IAMポリシー評価まわり

評価順序: **①明示Deny → ②SCP/権限境界等のガードレール → ③明示Allow → ④デフォルトDeny**（何もマッチしなければ拒否）。試験では「明示Denyは何があっても勝つ」という一点が繰り返し問われる。

| 項目 | 内容 | メモ | 検証Lab |
|------|------|------|---------|
| 明示Deny | ポリシー内で `"Effect": "Deny"` を明示したステートメント | 同じアクションに明示Allowと明示Denyが両方マッチしても**必ずDenyが勝つ**。IAMポリシー・SCP・リソースベースポリシー・権限境界のどこにあっても同様 | [004-s3-secure-transport](../labs/004-s3-secure-transport/)（`aws:SecureTransport`条件のDenyでHTTP強制） |
| 明示Allow | ポリシー内で `"Effect": "Allow"` を明示したステートメント | 明示Denyが存在しない場合のみ有効。IAMユーザー/ロールにアタッチされたポリシーのいずれか1つでもAllowすれば許可される（OR条件） | |
| デフォルトDeny | IAMの初期状態は「暗黙のDeny」＝すべて拒否 | どのポリシーにも明示Allowが無ければ、最終的にデフォルトDenyで拒否される。「許可リストに無ければ拒否」というホワイトリスト方式 | |
| SCPとの関係 | SCPはOrganizations配下のアカウントに対する**許可の上限（ガードレール）**であり、それ自体は権限を付与しない | SCPでDenyされているアクションは、対象アカウント内でIAMポリシーがどれだけAllowしていても実行不可。逆にSCPがAllowしているだけでは何も使えず、IAM側で別途Allowが必要（両方が揃って初めて許可）。権限境界（Permissions Boundary）も同じ「掛け算」の考え方 | |

## KMS

| 項目 | 内容 | メモ | 検証Lab |
|------|------|------|---------|
| AWS所有キー vs AWS管理キー vs カスタマー管理キー | AWS所有キー: サービス内部で使われ利用者からは不可視／AWS管理キー(`aws/xxx`): アカウント内で見えるがローテーション・キーポリシーは固定／カスタマー管理キー(CMK): ローテーション周期・キーポリシー・無効化/削除まで利用者が完全制御 | 「CloudTrailで復号者を監査したい」「鍵を無効化/削除して即座にアクセス遮断したい」「クロスアカウントでキーを共有したい」→ カスタマー管理キーが必須（AWS所有キーではそもそも不可能） | [002-dynamodb-sse](../labs/002-dynamodb-sse/) |
| キーポリシー vs IAMポリシー | キーポリシーはKMSキーにアタッチされるリソースベースポリシーで、**そのキーへのアクセス可否の大元**。IAMポリシーだけでは不十分で、キーポリシー側で該当プリンシパルへの許可（`Enable IAM User Permissions`ステートメント等）が必要 | キーポリシーのデフォルト（コンソール作成時）はルートアカウントに `kms:*` を許可し、実質的な制御をIAMポリシーに委譲する形。キーポリシーが管轄するのは暗号化/復号などKMS APIの可否のみで、S3やネットワーク層のアクセス制御は管轄外 | |
| エンベロープ暗号化 | KMSの直接暗号化は4KBまでのため、`GenerateDataKey`でDEK（データキー）を取得し実データはローカルで暗号化、DEK自体はKMSキーで暗号化して一緒に保存する方式 | 平文DEKは使用後即破棄、暗号化DEKは保存してよい（KMSキーへのアクセス権が無ければ復号不可なため）。暗号化コンテキストで取り違え防止・改ざん検知ができる（非対称鍵では使えない） | [003-envelope-encryption](../labs/003-envelope-encryption/) |

## Secrets Manager vs Systems Manager Parameter Store

| 観点 | Secrets Manager | Parameter Store | 検証Lab |
|------|------------------|------------------|---------|
| 自動ローテーション | Lambdaによるネイティブな自動ローテーションを標準サポート（RDS/Redshift/DocumentDB等はテンプレートあり、それ以外も自作Lambdaで対応可） | ローテーション機能自体は無い。EventBridge等と自作Lambdaを組み合わせて自前で実装する必要がある | |
| 料金 | シークレット数＋APIコール数に応じた有料サービス | Standardパラメータは無料。Advancedパラメータ（サイズ拡張・自動ローテーション連携・高頻度取得）は有料 | |
| 主な用途 | DB認証情報など「定期的なローテーションが必須」の機密情報 | アプリ設定値・環境変数・機密性の低い値。KMS連携でSecureString化すれば機密情報も保管可（ただし自動ローテーションは無い） | [012-secretsmanager-replication](../labs/012-secretsmanager-replication/) |
| クロスリージョン | ネイティブなレプリケーション機能あり（既存シークレットに「レプリカリージョンを追加」するだけ。暗号化キーはレプリカ側リージョンのKMSキーを指定） | ネイティブなクロスリージョン複製機能は無い | [012-secretsmanager-replication](../labs/012-secretsmanager-replication/) |
| 判断のコツ | 設問に「ローテーション」「DB認証情報」「クロスリージョン複製」が出たらSecrets Manager優位 | 設問が「コストを抑えたい」「単なる設定値/階層管理」ならParameter Store優位 | |

## クロスアカウントアクセス・リソース共有

「アカウントAのリソースをアカウントBから、複製せず・運用オーバーヘッド最小でアクセスさせたい」という設問で並ぶ定番の選択肢と、それぞれが不正解になる理由。

| 方法 | 概要 | 複製の要否 | 運用オーバーヘッド | 不正解になりがちな理由 |
| ---- | ---- | ---- | ---- | ---- |
| **AWS RAM（Resource Access Manager）** | リソース共有をRAM側で一度設定するだけで、他アカウント（またはOrganizations経由で組織全体）から直接参照可能にする | 不要（ARNで直接参照） | 最小（初回設定のみ） | ―（このパターンでは正解になりやすい） |
| クロスアカウントIAMロール（AssumeRole） | アカウントAにロールを作成し、信頼ポリシー＋許可ポリシーを設定。アカウントB側でAssumeRoleを実装 | 不要 | 中〜高（ロール作成・信頼ポリシー・許可ポリシー・呼び出し側実装が必要） | 技術的には有効だが設定手順が多い |
| リソースを別ストレージ（S3等）にコピーするスクリプト | 値をエクスポートして共有可能な場所に置く | **必要**（実質的に複製） | 高（スクリプト保守＋定期実行＋同期処理が別途必要） | 「複製しない」という要件に反する |
| IAMユーザーの長期認証情報を共有 | アカウントAのアクセスキー／シークレットキーをアカウントBのアプリに埋め込む | 不要 | 高（ローテーション・保管の負荷、漏洩リスク大） | セキュリティベストプラクティス違反として即アウト |

### AWS RAMの対応リソース例（DVA目線）

- Systems Manager Parameter Store のパラメータ
- VPCのサブネット（shared VPC）
- License Manager の設定
- Transit Gateway
- Route 53 Resolver ルール

### 判断のコツ

- 選択肢に「スクリプトでコピー」「S3に保存」等が出たら → 複製が発生するので「複製しない」という要件と矛盾しないか確認
- 「運用オーバーヘッド最小」というフレーズがあり、対応リソースタイプ（上記5つなど）に該当するなら → AWS RAMを疑う
- AssumeRoleはRAMより設定ステップが多いため、両方が選択肢にある場合はRAMが優先されやすい
- AWS Organizationsと組み合わせた「組織全体へ一括共有」もRAMの文脈で問われる
