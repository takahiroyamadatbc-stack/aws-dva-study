# セキュリティ・権限メモ

IAM、KMS、Secrets Manager／Parameter Store周りの暗記事項。

## IAMポリシー評価まわり

評価順序: **①明示Deny → ②SCP/権限境界等のガードレール → ③明示Allow → ④デフォルトDeny**（何もマッチしなければ拒否）。試験では「明示Denyは何があっても勝つ」という一点が繰り返し問われる。

| 項目 | 内容 | メモ | 検証Lab |
|------|------|------|---------|
| 明示Deny | ポリシー内で `"Effect": "Deny"` を明示したステートメント | 同じアクションに明示Allowと明示Denyが両方マッチしても**必ずDenyが勝つ**。IAMポリシー・SCP・リソースベースポリシー・権限境界のどこにあっても同様 | [004-s3-secure-transport](../labs/004-s3-secure-transport/)（`aws:SecureTransport`条件のDenyでHTTP強制） |
| 明示Allow | ポリシー内で `"Effect": "Allow"` を明示したステートメント | 明示Denyが存在しない場合のみ有効。IAMユーザー/ロールにアタッチされたポリシーのいずれか1つでもAllowすれば許可される（OR条件） | |
| デフォルトDeny | IAMの初期状態は「暗黙のDeny」＝すべて拒否 | どのポリシーにも明示Allowが無ければ、最終的にデフォルトDenyで拒否される。「許可リストに無ければ拒否」というホワイトリスト方式 | |
| SCPとの関係 | SCPはOrganizations配下のアカウントに対する**許可の上限（ガードレール）**であり、それ自体は権限を付与しない | SCPでDenyされているアクションは、対象アカウント内でIAMポリシーがどれだけAllowしていても実行不可。逆にSCPがAllowしているだけでは何も使えず、IAM側で別途Allowが必要（両方が揃って初めて許可）。権限境界（Permissions Boundary）も同じ「掛け算」の考え方 | |

## KMS

| 項目 | 内容 | メモ | 検証Lab |
|------|------|------|---------|
| AWS所有キー vs AWS管理キー vs カスタマー管理キー | AWS所有キー: サービス内部で使われ利用者からは不可視／AWS管理キー(`aws/xxx`): アカウント内で見えるがローテーション・キーポリシーは固定／カスタマー管理キー(CMK): ローテーション周期・キーポリシー・無効化/削除まで利用者が完全制御 | 「CloudTrailで復号者を監査したい」「鍵を無効化/削除して即座にアクセス遮断したい」「クロスアカウントでキーを共有したい」→ カスタマー管理キーが必須（AWS所有キーではそもそも不可能） | [002-dynamodb-sse](../labs/002-dynamodb-sse/) |
| キーポリシー vs IAMポリシー | キーポリシーはKMSキーにアタッチされるリソースベースポリシーで、**そのキーへのアクセス可否の大元**。IAMポリシーだけでは不十分で、キーポリシー側で該当プリンシパルへの許可（`Enable IAM User Permissions`ステートメント等）が必要 | キーポリシーのデフォルト（コンソール作成時）はルートアカウントに `kms:*` を許可し、実質的な制御をIAMポリシーに委譲する形。キーポリシーが管轄するのは暗号化/復号などKMS APIの可否のみで、S3やネットワーク層のアクセス制御は管轄外 | |

### エンベロープ暗号化とDEK（データキー）

KMSの`Encrypt`/`Decrypt`で直接暗号化できるのは**最大4KBまで**で、大量データを毎回KMSに送るのも性能・コストの面で非現実的。そこで鍵の管理はKMSに任せ、実データの暗号化はローカルで行う方式が**エンベロープ暗号化**で、ローカル暗号化に使う鍵が**DEK（Data Encryption Key）**。

```
KMSキー（CMK）  ─ 外に出ない。ARNで参照するのみ
     │ GenerateDataKey
     ▼
DEK（平文）───────→ ローカルでデータを暗号化 → 使用後ただちに破棄
DEK（暗号化済み）──→ 暗号化データと一緒に保存
```

#### DEKを自分で扱う場面 / 扱わない場面

| 対象 | 使うAPI | DEKを意識するか |
|---|---|---|
| 4KB以下（パスワード、トークン、設定値） | `Encrypt` / `Decrypt` を直接 | 不要 |
| 4KB超（ファイル、DBレコード群、ログ） | `GenerateDataKey` → ローカル暗号化 | 必要 |
| S3 / DynamoDB / EBS / RDS のSSE | 自分では何も呼ばない | 不要（AWSが内部で実施） |

マネージドサービスのSSEも内部ではエンベロープ暗号化を使っているが、DEKの生成・破棄・保存はサービス側が行うため利用者からは見えない。自分でDEKを扱うのは、クライアントサイド暗号化・フィールドレベル暗号化（テーブル全体のSSEとは別に特定属性だけ追加暗号化）・AWS外への持ち出し・自前のバックアップ処理などのケース。

#### API 3種

| API | 返るもの | 用途 |
|---|---|---|
| `GenerateDataKey` | 平文DEK + 暗号化DEK | 今すぐ暗号化する |
| `GenerateDataKeyWithoutPlaintext` | 暗号化DEKのみ | 後で使う／呼び出し側が平文を持ちたくない |
| `Decrypt` | 平文DEK | 復号時（暗号化DEKを渡す。対称鍵なら`--key-id`不要、暗号文ブロブに鍵情報が含まれる） |

実装の鉄則：**平文DEKは使用後即座に破棄**し保存しない。**暗号化DEKは暗号化データの隣に保存してよい**（KMSキーへのアクセス権が無ければ復号不可なため）。

#### 暗号化コンテキスト（Encryption Context）

暗号化時に添えるキーと値のペア（例: `--encryption-context tenant=acme,table=users`）。

- 暗号化されない（平文のままメタデータとして保持される）。AES-256-GCMのAAD（Additional Authenticated Data）として使われ、改ざん検知の対象になる
- 復号時は暗号化時と**完全に同じ**キー・値が必要（過不足・変更があれば`InvalidCiphertextException`）
- 対称鍵では任意（付けるのがベストプラクティス）、**非対称鍵では概念自体が存在しない**（試験のひっかけ対象）
- 鍵導出には使われない（パスワードのソルトとは役割が異なる）。秘密情報を値に入れてはいけない（CloudTrailに平文で記録される）

| 目的 | 内容 |
|---|---|
| 取り違え事故の防止 | 別テナント／別リソース用のDEKを誤って復号しようとした場合に失敗させる |
| 改ざん検知 | 暗号文とコンテキストの組み合わせが変えられていないかをGCMのAADで保証 |
| 監査証跡 | CloudTrailの`Encrypt`/`Decrypt`/`GenerateDataKey`イベントに平文で記録される |
| ポリシーの条件句 | `kms:EncryptionContext:<key>` でIAM/キーポリシーから制御できる |

#### データキーキャッシング

同じDEKを一定回数・一定時間だけ再利用する仕組み（AWS Encryption SDK）。KMS呼び出し回数を減らしコスト・レイテンシを改善できる一方、1つのDEKが守るデータ量が増えるため漏洩時の影響範囲が拡大するトレードオフがある。高スループット用途で検討する。

#### 動作確認（CLI）

```bash
KEY_ID=$(aws kms create-key --description "envelope-encryption-test" \
  --tags TagKey=Project,TagValue=dva-study --query KeyMetadata.KeyId --output text)

# 4KB制限の確認（5KBのデータはEncryptで失敗する）
dd if=/dev/urandom of=big.bin bs=1024 count=5
aws kms encrypt --key-id $KEY_ID --plaintext fileb://big.bin   # → 失敗

# DEK生成（平文DEK + 暗号化DEKが返る）
aws kms generate-data-key --key-id $KEY_ID --key-spec AES_256 \
  --encryption-context purpose=test > dek.json

# 暗号化コンテキストを変えて復号 → InvalidCiphertextException
aws kms decrypt --ciphertext-blob fileb://dek.enc \
  --encryption-context purpose=different
```

#### 試験でのキーワード対応

| 設問の語 | 対応する答え |
|---|---|
| 4KBを超えるデータを暗号化 | `GenerateDataKey` によるエンベロープ暗号化 |
| KMS呼び出し回数・コストを削減 | データキーキャッシング |
| 暗号化を後で行う／平文鍵を持ちたくない | `GenerateDataKeyWithoutPlaintext` |
| 復号時の意図しない取り違えを防ぐ | 暗号化コンテキスト |
| AWSにも平文を見せたくない | クライアントサイド暗号化 |
| 非対称鍵 + 暗号化コンテキスト | 誤り（非対称鍵では使えない） |

### S3の保存時暗号化：SSE-S3 / SSE-KMS（AWSマネージド）/ SSE-KMS（カスタマーマネージド）

| 項目 | SSE-S3 | SSE-KMS（AWSマネージドキー `aws/s3`） | SSE-KMS（カスタマーマネージドキー/CMK） |
| --- | --- | --- | --- |
| 鍵の管理者 | S3が内部で完結（KMSに一切現れない） | KMS上の自動生成キー | ユーザーがKMSで作成・管理 |
| キーポリシー | 設定不可 | 設定不可（AWS管理） | 自由に設定可能（プリンシパル単位で細かく制御） |
| ローテーション | AWS内部で自動・不可視・制御不可 | 自動のみ（年1回固定、オンデマンド不可） | 自動ローテーション（年1回）に加え **オンデマンドローテーション**（`RotateKeyOnDemand`）も可能 |
| CloudTrail監査 | KMS API呼び出しの記録なし（復号者の粒度が粗い） | KMS API呼び出しが記録される（`Decrypt`/`GenerateDataKey`等） | 同左＋キー単位でのアラート・追跡がしやすい |
| クロスアカウント共有 | 不可 | 不可 | キーポリシー＋grantで可能 |
| 削除・無効化による即時アクセス遮断 | 不可 | 不可 | 可能 |
| 追加コスト | なし | KMS APIリクエスト課金（約$0.03/1万リクエスト） | 同左のAPI課金＋キーの月額固定費（約$1/キー/月） |
| 選ぶ基準 | コンプライアンス要件が特にない一般データ | 「KMSで暗号化」だけ必要で鍵管理はAWS任せでよい場合 | オンデマンドローテーション／監査／クロスアカウント共有／即時遮断が必要な場合（個人データ等） |

判断のコツ：設問に「オンデマンドでローテーション」「クロスアカウントで共有」「CloudTrailで復号者を監査」「鍵を無効化して即座にアクセス遮断」のいずれかが出たら、選択肢はカスタマーマネージドキー一択（AWSマネージドキー・SSE-S3ではそもそも不可能）。それ以外の一般的な保存時暗号化要件ならSSE-S3で十分というのが基本線。転送中暗号化（`aws:SecureTransport`）とセットで問われることが多い。検証Lab: [004-s3-secure-transport](../labs/004-s3-secure-transport/)

### S3 vs RDS vs DynamoDBの暗号化：単位と有効化タイミングの違い

- **S3**: オブジェクト単位でSSE-S3 / SSE-KMSを選べる。バケットデフォルト暗号化はいつでも変更可能で、既存オブジェクトへの遡及適用も（再アップロードやバッチオペレーションで）可能
- **RDS**: 暗号化は**インスタンス作成時にしか有効化できない**。既存の未暗号化インスタンスを暗号化する場合はスナップショット取得→暗号化コピー→そこから復元という手順が必要。対象はストレージボリューム全体（データファイル・自動バックアップ・スナップショット・リードレプリカ・ログまで）で、S3のようにオブジェクト単位の選択はない。鍵はAWSマネージドキー(`aws/rds`)かCMKを選択（考え方はS3のSSE-KMSと同じ）
- **DynamoDB**: 暗号化は常時有効（無効化不可）。鍵は3段階選べ、S3のSSE-S3に相当する「KMS外で完結する層」が**AWS所有キー**として明示的に存在する点がS3と異なる（AWS所有キー＝SSE-S3相当／AWS管理キー`aws/dynamodb`＝SSE-KMS AWSマネージド相当／CMK＝SSE-KMS CMK相当）。検証Lab: [002-dynamodb-sse](../labs/002-dynamodb-sse/)

## Secrets Manager vs Systems Manager Parameter Store

| 観点 | Secrets Manager | Parameter Store | 検証Lab |
|------|------------------|------------------|---------|
| 自動ローテーション | Lambdaによるネイティブな自動ローテーションを標準サポート（RDS/Redshift/DocumentDB等はテンプレートあり、それ以外も自作Lambdaで対応可） | ローテーション機能自体は無い。EventBridge等と自作Lambdaを組み合わせて自前で実装する必要がある | |
| 料金 | シークレット数＋APIコール数に応じた有料サービス | Standardパラメータは無料。Advancedパラメータ（サイズ拡張・自動ローテーション連携・高頻度取得）は有料 | |
| 主な用途 | DB認証情報など「定期的なローテーションが必須」の機密情報 | アプリ設定値・環境変数・機密性の低い値。KMS連携でSecureString化すれば機密情報も保管可（ただし自動ローテーションは無い） | [012-secretsmanager-replication](../labs/012-secretsmanager-replication/) |
| クロスリージョン | ネイティブなレプリケーション機能あり（既存シークレットに「レプリカリージョンを追加」するだけ。暗号化キーはレプリカ側リージョンのKMSキーを指定） | ネイティブなクロスリージョン複製機能は無い | [012-secretsmanager-replication](../labs/012-secretsmanager-replication/) |
| 判断のコツ | 設問に「ローテーション」「DB認証情報」「クロスリージョン複製」が出たらSecrets Manager優位 | 設問が「コストを抑えたい」「単なる設定値/階層管理」ならParameter Store優位 | |

### Secrets Managerのローテーション戦略：シングルユーザー vs 交代ユーザー

**頻出。**「ダウンタイムなし」「高可用性」というキーワードとセットで出やすい定番論点。

シークレットのローテーションは「①ローテーションのやり方（戦略）」と「②ローテーションを誰が実装するか（マネージド or 自作Lambda）」という**独立した2つの軸**で決まる。この2軸を混同すると誤答しやすい。

#### 軸1: ローテーション戦略（更新方法）

| 戦略 | 内容 | ダウンタイム |
| ---- | ---- | ---- |
| シングルユーザー（Single user） | 既存のDBユーザー1人のパスワードを直接上書き更新する | 更新の瞬間、旧パスワードを使っている接続が失敗しうる。**ダウンタイムのリスクあり** |
| 交代ユーザー（Alternating users） | あらかじめ用意した2人目のユーザー（例: `MyUser` / `MyUserClone`）に交互に切り替える。新シークレットを先に用意してから古い方から新しい方へ徐々に切り替える | 新旧どちらのユーザーも有効な状態を経由するため、切り替え中も接続が途切れない。**高可用性・無停止ローテーションを実現** |

#### 軸2: 実装方式（マネージド or カスタムLambda）

| 実装方式 | 対応DB | 備考 |
| ---- | ---- | ---- |
| マネージドローテーション | **RDS（MySQL/PostgreSQL/Oracle/SQL Server等）、Amazon DocumentDB、Amazon Redshift**など、AWSが管理するデータベースサービスのみ | AWSがローテーション用Lambda関数（テンプレート）を自動生成してくれるため実装不要 |
| カスタムLambda関数によるローテーション | **上記以外すべて**（EC2上に自前構築したDB、オンプレDB、サードパーティAPIキー等） | ローテーション処理（新認証情報の作成／DB側への反映／シークレットの更新）を自分でLambda関数として実装する必要がある |

#### ローテーション戦略の判断のコツ

- 「EC2で構築したデータベース」「オンプレミス」「マネージドサービスではないDB」→ マネージドローテーションは**選択肢としてそもそも存在しない**（RDS/DocumentDB/Redshift等でしか使えない）。必ずカスタムLambdaになる
- 「ダウンタイムなし」「高可用性」「接続を維持したまま」→ 戦略は**交代ユーザー**一択（シングルユーザーは仕組み上ダウンタイムのリスクを排除できない）
- この2軸は独立しているため、「EC2上のDB」×「交代ユーザー戦略」×「カスタムLambda」という組み合わせが正解になる問題が典型（マネージドローテーション×交代ユーザーは誤り選択肢の定番）

## クロスアカウントアクセス・リソース共有

「アカウントAのリソースをアカウントBから、複製せず・運用オーバーヘッド最小でアクセスさせたい」という設問で並ぶ定番の選択肢と、それぞれが不正解になる理由。

| 方法 | 概要 | 複製の要否 | 運用オーバーヘッド | 不正解になりがちな理由 |
| ---- | ---- | ---- | ---- | ---- |
| **AWS RAM（Resource Access Manager）** | リソース共有をRAM側で一度設定するだけで、他アカウント（またはOrganizations経由で組織全体）から直接参照可能にする | 不要（ARNで直接参照） | 最小（初回設定のみ） | ―（このパターンでは正解になりやすい） |
| クロスアカウントIAMロール（AssumeRole） | アカウントAにロールを作成し、信頼ポリシー＋許可ポリシーを設定。アカウントB側でAssumeRoleを実装 | 不要 | 中〜高（ロール作成・信頼ポリシー・許可ポリシー・呼び出し側実装が必要） | 技術的には有効だが設定手順が多い |
| リソースを別ストレージ（S3等）にコピーするスクリプト | 値をエクスポートして共有可能な場所に置く | **必要**（実質的に複製） | 高（スクリプト保守＋定期実行＋同期処理が別途必要） | 「複製しない」という要件に反する |
| IAMユーザーの長期認証情報を共有 | アカウントAのアクセスキー／シークレットキーをアカウントBのアプリに埋め込む | 不要 | 高（ローテーション・保管の負荷、漏洩リスク大） | セキュリティベストプラクティス違反として即アウト |

### AWS RAMの対応リソース例（DVA目線）

- Systems Manager Parameter Store のパラメータ
- VPCのサブネット（shared VPC）
- License Manager の設定
- Transit Gateway
- Route 53 Resolver ルール

### 判断のコツ

- 選択肢に「スクリプトでコピー」「S3に保存」等が出たら → 複製が発生するので「複製しない」という要件と矛盾しないか確認
- 「運用オーバーヘッド最小」というフレーズがあり、対応リソースタイプ（上記5つなど）に該当するなら → AWS RAMを疑う
- AssumeRoleはRAMより設定ステップが多いため、両方が選択肢にある場合はRAMが優先されやすい
- AWS Organizationsと組み合わせた「組織全体へ一括共有」もRAMの文脈で問われる
