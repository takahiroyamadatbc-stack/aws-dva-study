# 非同期処理の連携・失敗ハンドリング比較メモ（Lambda Destinations / EventBridge / SNS / SQS / Step Functions）

「Lambda関数Aの処理結果（特に失敗）を関数Bに伝える」ような非同期処理間の連携で、どのサービスを選ぶかは試験の頻出パターン。共通して問われるのは「**機能的にはどれでも実現できるが、要件（最小の開発作業/条件分岐の要否/多段ワークフローの要否）に対して過剰でないか**」という視点。

## 比較表

| サービス | 呼び出し方式 | 対応関係 | 条件分岐 | 実装コスト | 向いているケース |
| -------- | ------------ | -------- | -------- | ---------- | ----------------- |
| **Lambda Destinations** | push（非同期呼び出しの成功/失敗を検知して自動転送） | 1対1（on-success/on-failureそれぞれ1つずつしか設定不可） | 不可（送信先は固定。分岐したいなら受け手側で判定） | 最小（`put-function-event-invoke-config`の設定のみ、コード変更不要） | 単純な1系統のフォールバック・後処理。「非同期呼び出しの結果を別サービスに渡したいだけ」 |
| **EventBridge（Destinationsのターゲットとして）** | push（Lambda Destinationsの送信先をEventBridgeにし、ルールでさらに振り分け） | 1対多（イベントパターンにマッチする複数ルール→複数ターゲット） | 可能（`responsePayload.errorType`等でコンテンツベースルーティング） | 小〜中（ルール定義が増える分だけDestinations単体より手間） | 失敗原因ごとに異なる処理をしたい、他システムにも同じイベントを流したい |
| **Amazon SNS** | push（Pub/Sub、トピックにパブリッシュすると全サブスクライバーに配信） | 1対多（ファンアウト。同じメッセージのコピーが全員に届く） | 不可（サブスクリプションフィルターで絞り込みは可能だが、条件分岐そのものではない） | 小（トピック作成＋サブスクライブ） | 同じイベントを複数の独立したシステムに同時通知したい（例: 失敗通知をSlack連携用Lambda・監査ログ用Lambda・アラート用Lambdaに同時配信） |
| **Amazon SQS（ポーリング）** | pull（コンシューマがキューをポーリング、またはLambdaのEvent Source Mappingで擬似push化） | 1対1〜1対多（複数コンシューマで負荷分散も可） | 不可（メッセージ内容で分岐するにはコンシューマ側の実装が必要） | 中（キュー作成＋送信側のコード修正＋受信側のポーリング/Event Source Mapping設定） | 処理の急増をバッファリングしたい、コンシューマの処理速度に合わせて非同期に捌きたい、リトライやDLQを自前で細かく制御したい |
| **AWS Step Functions** | push（ステートマシンとして各ステップを呼び出し・分岐・リトライを制御） | 1対多（複雑な分岐・並列・リトライ・タイムアウトを状態遷移として定義） | 可能（Choice状態・Catch/Retryをネイティブサポート） | 大（ステートマシン定義＋起動用のEventBridgeルール等＋IAMロール） | 複数ステップにまたがる複雑なワークフロー、可視化・監査証跡が必要な業務プロセス、長時間実行（〜1年）の待機を含む処理 |

## 見分け方のコツ

- 「**単純なフォールバック**」「**成功/失敗の通知先を変えたいだけ**」→ Lambda Destinations
- 「**失敗の原因ごとに別処理をしたい**」「**同じイベントを複数の異なる仕組みに流したい**」→ EventBridge（コンテンツベースルーティング）
- 「**同じ内容を複数の独立した宛先に同時配信**」（ファンアウト）→ SNS
- 「**急なトラフィックのバッファリング**」「**コンシューマ側のペースで処理したい**」「**メッセージの永続化・可視性タイムアウトが欲しい**」→ SQS
- 「**多段階のワークフロー**」「**Choice/Retry/Catchなどの制御構造そのものが要件**」「**実行状況を可視化したい**」→ Step Functions
- 選択肢に複数のサービスの組み合わせ（EventBridgeルール＋複数Lambda、など）が出てきたら、まず「本当にその複雑さが必要な要件か」を問題文から確認する。「最小限の開発作業」「最もシンプルな」という文言があれば、オーケストレーション系（Step Functions）やファンアウト系（SNS）は基本的に過剰と判断してよい

## 各サービスの深掘りポイント

### Lambda Destinations

- 対象は**非同期呼び出し**（S3イベント通知・EventBridge経由の呼び出しなど）のみ。同期呼び出し（API Gateway経由など）には使えない
- on-failureが発火するのは**リトライ（デフォルト最大2回）をすべて使い切った後**。同一原因（例: 巨大画像によるタイムアウト）だと数回リトライしても同じ結果になりやすく、即座にフォールバックされるわけではない
- 受け手が受け取るのは元のイベントそのものではなく **invocation record**（`requestContext`/`requestPayload`/`responseContext`/`responsePayload`を含むラップされたJSON）。元のイベントは`requestPayload`の中に入っている
- タイムアウトはランタイムによる強制終了のため、関数内の`try/except`では捕捉できない。これがコード内エラーハンドリングではなく外部メカニズム（Destinations）が必要な理由

### EventBridge（失敗ルーティングの高度化）

- Lambda DestinationsのOnFailure先をEventBridgeにすると、invocation recordがイベントとしてEventBridgeに流れる
- ルールのevent patternで`detail.responsePayload.errorType`や`detail.requestContext.condition`にマッチさせることで、原因別に異なるLambda/SQS/SNS等へ振り分けられる
- コード変更なし・ステートマシンなしで「条件分岐するルーティング」を実現できるのが強み

### Amazon SNS

- Pub/Sub型のファンアウト。1つのメッセージが複数のサブスクライバーに**同じ内容のコピー**として配信される
- サブスクリプションフィルターポリシーでメッセージ属性による絞り込みは可能だが、あくまで「配信するかしないか」の判定であり、EventBridgeのような柔軟なコンテンツベースルーティングとは異なる
- SQS/Lambda/HTTP(S)/Emailなど多様なプロトコルをサブスクライバーにできる

### Amazon SQS（ポーリング）

- pull型なので、素の構成では**コンシューマ側が能動的にポーリング**する必要がある（LambdaならEvent Source Mappingでpush的に扱える）
- メッセージの可視性タイムアウト・DLQ・FIFOキューでの順序保証など、細かい制御をしたい場合に向く
- 送信側のコード修正が必要になる場合が多く（明示的に`SendMessage`を呼ぶ設計なら）、「最小限の開発作業」を問う設問では不利になりやすい

### AWS Step Functions

- Choice/Retry/Catch/Parallel/Waitなどをネイティブにサポートし、複雑な分岐・エラーハンドリングを**コードを書かずにJSON(ASL)で表現**できる
- 実行履歴が自動的に可視化される（デバッグ・監査に強い）ため、「処理の追跡可能性」が要件に含まれる設問では有力候補になる
- 逆に単純な1〜2ステップの連携にはオーバースペック。ステートマシン定義・起動トリガー（EventBridgeルール等）・IAMロールなど構築物が多い
